# D-08: `custom_perms` is not resolved in Firebase RTDB rules

**Status:** Approved (deferred) — fail-closed, no evidenced gap in current behavior.

**Decision:** Firebase Realtime Database security rules for the 17 accounting collections (and every other admin-gated collection: `finance`, `settings`, `users`) check only `role === 'admin'`, resolved via the `uid_lookup/{auth.uid} → appUserId → users/{appUserId}/role` chain. They do **not** attempt to also honor a non-admin user's `custom_perms` grant of `'finance'` (or any other permission). No rules migration to support this is planned as part of this phase, and none should be invented speculatively.

**Context:** The frontend (`firebase.js`'s `can(perm)`, `users.html`'s custom-permission editor) genuinely supports granting an individual permission — including `'finance'` — to a non-admin role via a `custom_perms` array stored on that user's own record (`users/{id}/custom_perms`). `can(perm)` checks this array with `Array.isArray(u.custom_perms) && u.custom_perms.includes(page)` (`firebase.js`, confirmed by direct read 2026-08-24). This means a real, currently-reachable app feature (granting a supervisor `'finance'` access without making them a full admin) exists on the client side with no server-side rule that recognizes it: today, such a user's frontend UI unlocks, but every actual read/write against an accounting collection they were "granted" access to is rejected by the RTDB rules, since those rules only ever check `role === 'admin'`.

**Why this isn't simply fixed by extending the rules:** `custom_perms` is stored as a plain RTDB array (object with numeric-string keys under the hood). The Firebase Rules language has no operator to ask "does this array contain the string `'finance'`" without knowing the exact index in advance — there is no `.includes()`/`contains()`-equivalent over an unbounded list in Realtime Database security rules (this is a Realtime-Database-specific limitation; Firestore's rules language does support this via `in`/array-contains on a document field, but this app uses RTDB). Writing a rule that "safely" handles this would require either: (a) a fixed, hardcoded set of array indices to check (fragile — silently stops working the moment the array's insertion order changes), or (b) restructuring `custom_perms` from an array into a keyed map (e.g. `custom_perms: {finance: true}`) so a direct `newData.child('custom_perms').child('finance').val() === true` check becomes possible. Option (b) is a real, viable fix — but it is a **data-shape migration** (touching every existing user record with a `custom_perms` array, plus `can()`'s read logic, plus `users.html`'s editor UI), not a rules-only change, and is explicitly out of scope for a security-hardening pass that was asked not to invent migrations.

**Current behavior is fail-closed, not fail-open:** the practical consequence of leaving this unresolved is that a non-admin user granted `'finance'` via `custom_perms` sees UI they cannot actually use (every accounting write/read attempt against the 17 hardened collections gets a real `403`/permission-denied from Firebase, not a silent bypass). This is the safe failure direction — it under-grants relative to the frontend's own intent, never over-grants. No security exposure results from leaving it as-is; the cost is a UX gap (a granted permission that doesn't work), not a vulnerability.

**Consequences of NOT migrating now:**
- Any non-admin user relying on a `custom_perms: ['finance']` grant to use accounting features will find every accounting page functionally broken (data won't load, writes will fail) even though the sidebar/nav lets them in. This is a real, user-visible product gap if any farm actually uses this grant today for `'finance'` specifically — not confirmed either way in this pass (out of scope to survey production user records).
- The 17 accounting collections remain, in practice, **admin-only**, regardless of what `custom_perms` says, until this is deliberately revisited.

**If this is revisited later**, the two real options are: (1) migrate `custom_perms` to a keyed-map shape and update rules + `can()` + the editor UI together as one atomic change, with a documented historical-data migration strategy for existing array-shaped records (same discipline as D-01/D-02/D-03/D-07's historical-data sections); or (2) explicitly decide `'finance'` (and any other admin-tier permission) can never be granted via `custom_perms` and enforce that constraint in `users.html`'s editor UI, closing the gap by making the frontend's promise match the rules' actual behavior instead of changing the rules. Neither is implemented here — this decision only records that the current state is intentional and safe, not silently broken.

**Verification:** Read `firebase.js`'s `can(perm)` implementation directly (confirms the array/`.includes()` shape). Read `database.rules.json`'s own header comment and every one of the 17 accounting collections' `.read`/`.write` rules directly (confirms every one uses the `role === 'admin'` chain exclusively, with no `custom_perms` reference anywhere in the rules file). No standalone decision record existed before this file; the substance was previously documented only inline as a code comment in `database.rules.json`.
