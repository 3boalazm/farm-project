# D-07: `submitBirthDirect()` convergence onto `createOffspringAnimal()`

**Status:** APPROVED, IMPLEMENTED (2026-08-23).

**Decision:** `submitBirthDirect()` (`pages/breeding.js:183`) stops building its own `animals` payload and calls `window.createOffspringAnimal()` per offspring instead — the same convergence D-02 and D-03 already made for `markBorn` and the AI `add_birth` path. No UI change; the form and its fields are untouched.

**Context:** `submitBirthDirect()` is the last of the four Birth entry points not on the canonical path (see `docs/certification/BIRTH.md`'s entry-point table). Comparing it directly against `_ubSubmit()` (the reference implementation, `shared.js:1941`) shows the breeding-record payload the two build is already identical field-for-field (`female_tag`, `mother_tag`, `birth_weights` as a string, etc.) — the divergence is narrowly in the animal-creation loop:

| | `submitBirthDirect()` (current) | `_ubSubmit()` via `createOffspringAnimal()` |
|---|---|---|
| Animal write | Inline `fbPost('animals',{...})`, once per offspring | `createOffspringAnimal(p)`, once per offspring |
| `mother_id`/`father_id` | Never set | Resolved via `findByTag()` when not already known |
| `birth_weight` on the animal doc | Never set | `p.weight\|\|null` |
| Weight history (`animals/{id}/weights`) | Never written | Written when a weight was given |
| `notes` on the animal doc | Never set (only on the `breeding` record) | `p.notes\|\|null` |
| Per-offspring tag suffix (qty>1) | `tag+'-'+ar(i+1)` (Arabic-Indic digit) | `tag+'-'+(i+1)` (plain digit) — a pre-existing, unrelated inconsistency between the two paths, noted here since it's visible in the same code but not part of this decision |

**Evidence considered:**
- `docs/certification/BIRTH.md` — genealogy is described as "confirmed working for all four entry points" because `pedigree.js` only reads `mother_tag`/`father_tag` strings, not `mother_id`/`father_id`. Converging does not fix a *broken* genealogy path; it backfills the `_id` links that other, currently-unused-for-this-path features (repairGenealogy(), any future ID-based lookup) would need. Framed accurately, this decision closes a **consistency gap**, not a live genealogy bug.
- Weight: animals born via this form are invisible to the certified Weight SSOT (`animals/{id}/weights`) and to `evaluateWeightAlert()`/production dashboards until their first post-birth weigh-in — a real, user-visible gap for a farm that uses this specific entry point (the "مواليد جديدة" direct-registration modal, distinct from the Unified Birth modal `_ubSubmit` normally used).
- No other file reads the `submitBirthDirect`-created animals expecting the *absence* of `mother_id`/`father_id`/`birth_weight`/history — i.e., nothing was found treating the current gap as a feature to preserve.

**Consequences (if approved and implemented):**
- Animals created through this form gain: resolved mother/father IDs where resolvable, a `birth_weight` field on the animal document, a weight-history entry when a birth weight was entered, and `notes` copied onto the animal record.
- No consequence to `breeding` records — the payload built for that collection is unchanged.
- No consequence to `offspring_count`/`male_offspring`/`female_offspring` aggregate fields — still written exactly as today.
- Historical animals created by the old inline path remain exactly as they are — this is a going-forward change only, matching D-02/D-03's own historical-data strategy (no synthesized backfill).

**Historical Strategy:** Same as D-02/D-03 — leave animals already created via the old inline path untouched. Their missing `mother_id`/`father_id`/`birth_weight`/weight-history were never captured and any backfill would manufacture false-precision records.

**Implementation:** replaced the `for(let i=0;i<qty;i++){ await fbPost('animals',{...}) }` loop in `submitBirthDirect()` with a loop calling `await window.createOffspringAnimal({species,breed,gender,purpose,birthDate,tag,motherTag,motherBreed,fatherTag,weight,barn,notes})`, mirroring `_ubSubmit()`'s own loop shape. `weight` is read once, alongside this function's other pre-`closeModal()` field reads (same field-read-timing rule already documented inline in this function). Blast radius: `pages/breeding.js`, one function, no HTML/form changes.

**Verification:** `node --check` clean. Live-driven in-browser: opened the real modal (`window.openBirthModal()`), filled real form fields, stubbed `createOffspringAnimal`/`fbPost` to capture calls without hitting Firebase, and confirmed for both qty=2 (tagged) and qty=1 (untagged, no father, no weight) cases that: the `breeding` record payload is byte-identical to before; `createOffspringAnimal` is called once per offspring with the correct `motherTag`/`motherBreed`/`fatherTag`/`weight` (as a parsed number, not string)/`barn`/`notes`; the tag suffix (`ar(i+1)`, Arabic-Indic) is unchanged; and an empty tag correctly passes `null` so `createOffspringAnimal`'s own `generateAnimalTag()` fallback still fires.
