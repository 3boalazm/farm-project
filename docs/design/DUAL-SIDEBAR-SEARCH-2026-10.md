## 1 — ماذا وجدنا في التطبيق (قبل الإصلاح)

### 1.1 التركيب الفعلي

```
┌──────────┬────────────────────────────┬──────────┐
│  PANEL   │        page-wrap           │   RAIL   │  ≥1200px قبل الإصلاح
│  300px   │      (المحتوى)             │   80px   │  = 380px مقتطعة
│ (يسار)   │                            │ (يمين)  │
└──────────┴────────────────────────────┴──────────┘
  + appbar (fixed, 60px) + bottomnav (<992px) + command palette (⌘K)
  = 4 أسطح تنقل دائمة في نفس الوقت
```

السورس:

- `styles.css:509` — `margin-right:80px; margin-left:300px` على `.page-wrap.rail-v2-content` (محتوى محشور في 820px على شاشة 1200px).
- `ui.css:766` — `shell-end:300px` على ≥1200px (نفس الافتراض مكرر في نظامَي ثيمز).
- `shared.js:renderNavbarV2` — يبني `rail-v2` (يمين) + `rail-v2-panel` (يسار) + `rail-v2-backdrop` + `rail-v2-mobile-bar/bottomnav`.

### 1.2 محتوى كل لوحة

| اللوحة | ماذا تحمل | هل تستحق مساحة دائمة؟ |
|--------|-----------|------------------------|
| **Rail (80px)** | شعار + 4 أقسام قابلة للطي + أفاتار/ثيم | **نعم** — هو التنقل الأساسي الوحيد |
| **Panel (300px)** | بروفايل المستخدم + أزرار تنبيهات/تراجع/مساعد + info farm/date + اختصارات (4 روابط) + خروج | **لا** — كل عنصر فيها موجود أصلاً في الـ appbar أو في صفحة مخصصة (notifications.html / tasks.html / assistant.html) |
| **Appbar** | breadcrumbs + title + search trigger (⌘K) + quick-add + bell + theme + user menu | **نعم** — لكنه يكرر نفس معلومات الـ panel |
| **Bottomnav** | 5 وجهات + more | **نعم** على موبايل فقط |

الـ panel إذن **duplicate** وظيفياً: 80% من محتواه موجود في الـ appbar، والـ 20% الباقي (الاختصارات) يظهر في 3 أماكن أخرى. تثبيته يكلّف ثلث الشاشة مقابل فائدة هامشية.

### 1.3 السلوك غير المتسق

- موبايل: اللوحتان drawer مع backdrop + إغلاق بـ Escape/click خارج — سلوك صحيح.
- ديسكتوب: الـ panel ثابت (لا backdrop، لا Escape يغلقه، المحتوى ينزاح) — سلوك مختلف تماماً لنفس العنصر. المستخدم الذي تعلّم إغلاقه على الموبايل يفشل على الديسكتوب.

## 2 — بحث الحالات المشابهة (ماذا تفعل التطبيقات الأخرى بـ 2 سايد بار)

### 2.1 التصنيف

| النمط | مثال | متى ينجح | هل يناسبنا؟ |
|------|------|----------|-------------|
| **A — سايد بار واحد + بانل overlay** | Linear, Notion, Slack, Discord, Gmail, GitHub | اللوحة الثانوية معلومات سياقية/مستخدم/اختصارات لا تحتاج أن تراها طوال الوقت | **نعم** — حالتنا بالضبط |
| **B — سايد بارين ثابتين** | Jira (projects + issue detail), Figma (layers + properties), VS Code (explorer + outline) | كل لوحة تحمل أدوات تحرير مختلفة تُستخدم بالتوازي أثناء مهمة واحدة | **لا** — لا مهمة في المزرعة تتطلب رؤية التنقل + بروفايل المستخدم معاً |
| **C — سايد بار واحد قابل للطي + breadcrumbs** | ERPNext, FarmLogs, AgriWebb, Odoo | المحتوى هو الجداول/النماذج التي تحتاج كل العرض | **نعم** — بديل جيد إن أردنا دمج الـ panel كـ section داخل الـ rail الموسّع |
| **D — لا سايد بار، هيدر + تبويبات فقط** | Shopify admin (mobile-first) | التنقل ضحل (<10 صفحات) | **لا** — لدينا 30+ صفحة في 4 أقسام |

### 2.2 الدروس المستفادة

1. **المحتوى هو الملك في منتج operations.** كل بكسل يُقتطع للـ chrome هو بكسل يُفقد من جدول القطيع/النموذج المالي. النمط B يبرَّر فقط عندما يُستخدم اللوحان *أثناء نفس المهمة* (تحرير صورة: layers + properties). عندنا المهمة هي «إدخال/مراجعة»، والـ panel لا يشارك فيها.
2. **التكرار يقتل الثقة.** وجود user name/role/bell في مكانين (panel + appbar) يجعل المستخدم يتساءل «أيهما الصحيح؟» ويهدر الانتباه. مبدأ الـ Single Source of Truth للواجهة: كل معلومة لها مكان واحد ظاهر دائماً، والباقي عند الطلب.
3. **الـ overlay هو الحل الافتراضي للوحة غير أساسية.** كل تطبيقات النمط A تجعل الثانية overlay مع backdrop/dismiss. التثبيت الدائم هو الاستثناء الذي يحتاج تبريراً (ومفتاح pin صريح)، لا العكس.
4. **الموبايل هو الاختبار الحقيقي.** إن لم تستطع اللوحة أن تعمل كـ drawer على موبايل، فلن تعمل كـ persistent على ديسكتوب. عندنا الـ panel تعمل ممتاز كـ drawer — وهذا دليل أنها drawer بطبيعتها.

## 3 — القرار المعتمد في هذا الـ PR

### 3.1 المبدأ

> **الـ rail وحده ثابت. الـ panel overlay على كل المقاسات.**

- المحتوى (`page-wrap`) = كامل العرض ناقص الـ rail فقط (80px، أو 230px عند توسيع الـ rail). لا `margin-left` للـ panel إطلاقاً.
- الـ panel يظهر عند الطلب (أفاتار الـ rail أو زر `toggleRailPanel`) كـ overlay فوق المحتوى مع backdrop معتم. إغلاقه: backdrop click / زر X / `Escape` / اختيار رابط — نفس السلوك على موبايل وديسكتوب.
- الـ appbar يبقى كما هو (breadcrumbs + search + bell + user) — هو المصدر الوحيد الدائم لمعلومات المستخدم.

### 3.2 التغييرات الكودية الدقيقة

| ملف | ماذا تغيّر |
|-----|------------|
| `styles.css:503-510` | `margin-left:300px` → `0` افتراضياً؛ الـ panel `transform:translateX(-100%)` افتراضياً، `open` تُظهره مع backdrop. دعم legacy لـ `data-panel-v2="closed"` محفوظ. |
| `ui.css:760-769` | `shell-end:300px` عند ≥1200px → `0` دائماً. الـ appbar الآن يمتد كاملاً ناقص الـ rail فقط. |
| `shared.js:305-330` | `toggleRailPanel` يعكس منطق `open` صراحةً؛ `closeRailPanelDesktop()` جديد؛ backdrop/Escape/links تغلق الـ panel على الديسكتوب أيضاً. |

### 3.3 ما لم نفعله (عن قصد)

- **لم نحذف الـ panel markup.** نفس الـ HTML، نفس الروابط، نفس الأزرار — فقط تغيّر الـ CSS من `margin` إلى `overlay`. حذف الـ markup كان سيكسر اختبارات وروابط.
- **لم ندمج الـ panel داخل الـ rail الموسّع** (النمط C) — هذا إعادة تصميم أكبر تتطلب نقل 3 أقسام من الروابط واختبارها مع كل الأدوار. محفوظ كـ option مستقبلية (انظر §4).
- **لم نضف زر pin.** يمكن إضافته لاحقاً كـ preference (`localStorage['farm_panel_pinned']`) يعيد الـ 300px margin لمن يريد. الافتراضي يبقى overlay لأنه الأفضل للأغلبية (خاصة على شاشات المزرعة الصغيرة/التابلت).

## 4 — الخيارات المستقبلية (للمالك ليختار)

### الخيار 1 — كما هو الآن (المعتمد): overlay

- أقل مخاطرة، أقل كود، أكبر مكسب فوري (+300px).
- مناسب إن كانت الأولوية هي «المحتوى أوضح الآن».

### الخيار 2 — دمج الـ panel كـ expanded rail section

- عند توسيع الـ rail (230px) يظهر بداخله قسم خامس «حسابي / اختصاراتي» بدل لوحة منفصلة.
- يوحّد سلوك التوسيع (زر الشعار الوحيد يتحكم بكل شيء).
- يتطلب نقل `rail-v2-panel__*` إلى `rail-v2__section` خامسة + إعادة كتابة `buildSidebarNav` جزئياً.

### الخيار 3 — pin option

- زر دبوس في رأس الـ panel: `pinned` → `margin-left:300px` يعود؛ `unpinned` → overlay.
- يحفظ التفضيل في `localStorage` ويحترمه `ui.css` عبر `[data-panel-pinned="true"]`.
- مفيد لمدير المكتب على شاشة كبيرة يريد رؤية الاختصارات دائماً.

**التوصية:** ابق على الخيار 1 الآن، وقيّم الخيار 2/3 بعد أسبوع استخدام حقيقي — لا حاجة للتعقيد قبل التأكد أن المشكلة الأساسية (ضيق المحتوى) حُلّت.
