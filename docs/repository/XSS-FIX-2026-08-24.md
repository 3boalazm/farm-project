## assistant.html — treated separately, as instructed

The LLM's own output is untrusted input, not a special case exempted from escaping. Four sinks fixed:

1. **`addMsg()`** — the single choke point for every chat bubble (user input, LLM `info`/`clarify` responses, error messages). Previously did `div.innerHTML = String(text).replace(/\n/g,'<br>')` with no escaping. Now: `escapeHtml(String(text)).replace(/\n/g,'<br>')` — escape first, then convert literal newlines to real `<br>` tags. Order matters: escaping after the `<br>` conversion would have broken the intentional line breaks. One caller (`parsed.action==='info'`) was pre-converting `\n`→`<br>` itself before calling `addMsg`; that redundant call was removed so it doesn't double-process.
2. **`showConfirmation()`** — the pre-save "extracted data" preview. `parsed.summary` and any `data` key/value the LLM invented (not found in the fixed `fieldLabels`/`valueLabels` lookup tables) are now escaped.
3. **`editAndConfirm()`** — the edit modal's `mother_tag`/`notes` `value="..."` attributes, populated from LLM-extracted data.
4. **`showFarmContext()`** — escaped only at this HTML-rendering sink, deliberately **not** at `_farmContext`'s source, since that string is also concatenated as plain text into the LLM system prompt — escaping it there would corrupt what the model actually receives.

**Explicitly not claimed:** escaping these sinks fixes the *rendering* half of the risk (arbitrary HTML/script the model outputs can no longer execute). It does **not** address prompt injection — a tainted farm-data field (e.g., a medicine name) riding into the model's context, or a directly jailbroken response, could still cause the model to extract wrong data, recommend a wrong action, or produce a misleading `summary`/`answer`. That is a separate, unresolved business-logic/trust concern, tracked here as **REQUIRES FUTURE HARDENING**, not closed by this fix.

## pages/pedigree.js — treated separately, as instructed

Six sinks, several inside `aria-label` attributes (`renderNode`, `renderCenterNode`) where a value containing `"` could break out of the attribute. All fixed with `escapeHtml()`, verified with `< > " ' &` and real XSS probes (see Verification below) — the same helper correctly neutralizes both HTML-text and HTML-attribute contexts since it escapes `"`/`'` alongside `<`/`>`/`&`. Accessibility, Arabic names, and normal breed/tag rendering all confirmed unaffected.
