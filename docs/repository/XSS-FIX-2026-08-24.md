## assistant.html — treated separately, as instructed

The LLM's own output is untrusted input, not a special case exempted from escaping. Four sinks fixed:

1. **`addMsg()`** — the single choke point for every chat bubble (user input, LLM `info`/`clarify` responses, error messages). Previously did `div.innerHTML = String(text).replace(/\n/g,'<br>')` with no escaping. Now: `escapeHtml(String(text)).replace(/\n/g,'<br>')` — escape first, then convert literal newlines to real `<br>` tags. Order matters: escaping after the `<br>` conversion would have broken the intentional line breaks. One caller (`parsed.action==='info'`) was pre-converting `\n`→`<br>` itself before calling `addMsg`; that redundant call was removed so it doesn't double-process.
2. **`showConfirmation()`** — the pre-save "extracted data" preview. `parsed.summary` and any `data` key/value the LLM invented (not found in the fixed `fieldLabels`/`valueLabels` lookup tables) are now escaped.
3. **`editAndConfirm()`** — the edit modal's `mother_tag`/`notes` `value="..."` attributes, populated from LLM-extracted data.
4. **`showFarmContext()`** — escaped only at this HTML-rendering sink, deliberately **not** at `_farmContext`'s source, since that string is also concatenated as plain text into the LLM system prompt — escaping it there would corrupt what the model actually receives.

**Explicitly not claimed:** escaping these sinks fixes the *rendering* half of the risk (arbitrary HTML/script the model outputs can no longer execute). It does **not** address prompt injection — a tainted farm-data field (e.g., a medicine name) riding into the model's context, or a directly jailbroken response, could still cause the model to extract wrong data, recommend a wrong action, or produce a misleading `summary`/`answer`. That is a separate, unresolved business-logic/trust concern, tracked here as **REQUIRES FUTURE HARDENING**, not closed by this fix.

## pages/pedigree.js — treated separately, as instructed

Six sinks, several inside `aria-label` attributes (`renderNode`, `renderCenterNode`) where a value containing `"` could break out of the attribute. All fixed with `escapeHtml()`, verified with `< > " ' &` and real XSS probes (see Verification below) — the same helper correctly neutralizes both HTML-text and HTML-attribute contexts since it escapes `"`/`'` alongside `<`/`>`/`&`. Accessibility, Arabic names, and normal breed/tag rendering all confirmed unaffected.

## Verification

- **Syntax**: `node --check` on every edited `.js` file; every edited `.html` file's inline `<script>` blocks parsed with `new Function()` — all clean.
- **Full test suite**: `tests/smoke` (20/20), `tests/regression` (9/9), `tests/ssot` (2/2), new `tests/security/xss-hardening.spec.js` (7/7) — 39/39 passing after the fix.
- **Safety scan**: `node scripts/safety-scan.js` → 0 CRITICAL, 1 REVIEW (pre-existing, unrelated). A new **Check 4** was added as a lightweight regression guard: 27 exact `escapeHtml(...)` expressions, one per fixed sink, checked for continued presence — fails CRITICAL if any is removed. Verified the guard actually catches a regression (temporarily reverted one fix, confirmed the scan failed, restored it).
- **Live payload testing**: for the highest-priority sinks (`assistant.html`, `pages/pedigree.js`, `shared.js`'s shared components, `barns.html`, `births.html`, `goats.html`) — injected `<script>alert(1)</script>`, `<img src=x onerror=alert(1)>`, `">...` attribute-breakout, and `" ' < > &` directly through the real render functions in a live browser, asserted no `alert()` fired and no raw tag reached the DOM, and confirmed Arabic text and legitimate values still render/round-trip correctly. `pages/reports.js`'s 6 clusters were verified via static review + syntax/smoke tests only (all use the identical, already browser-proven `escapeHtml()` pattern) — not individually payload-tested live, given their lower priority tier (P1/P2) relative to assistant.html/pedigree.js (P0).

## Re-scan results — NOT all XSS is fixed repo-wide

A second, independent agent re-scanned the entire repository after this fix pass (not just re-checking the 25 original sites). Findings:

- **The 25 original sinks + the 1 caught regression (26 total): all confirmed fixed and verified.**
- **41 additional CONFIRMED VULNERABLE sinks found**, outside this phase's declared scope, across: `animals.html` (9 — the main animal list/cards, death/quarantine/sale modals), `animal-detail.html` (15 — page header, health/breeding/offspring tables, edit-modal attributes, a `<textarea>` breakout via `notes`), `import.html` (1 — the CSV/Excel import preview table, the root-cause entry point that lets a malicious value reach Firebase in the first place), `pages/health.js` (4 — the main list, sibling to the already-fixed detail modal), `pages/breeding.js` (4 — "upcoming births"/"return to heat" widgets and the edit modal, sibling to the already-fixed main list), `pages/vaccine.js` (1 — an "upcoming" banner, sibling to the fixed main list), `pages/production.js` (2 — the Summary tab leaderboard), `pages/tasks.js` (2 — an `aria-label` and an edit-modal attribute, sibling to an already-fixed text-content site), `shared.js` (1 — `renderInventoryStockIndicator()`, the one shared component not given the same treatment as its siblings), `cost.html` (1 — finance category, exploitable via a gap in `assistant.html`'s finance-entry path that skips the fixed list's own validation).
- **5 REQUIRES FUTURE HARDENING findings** (not reachable through any current UI, but unsafe if that ever changes): breed-catalog fields in `pages/reports.js`, `settings.html`, `assistant.html`, `animal-detail.html` (all sourced from `localStorage['farm_settings']`, no in-app way to inject a malicious value today), and `finance-reports.html`'s account names (the writing function `createAccount()` exists and is unsanitized, but no page currently calls it).

**A clear pattern emerged**: where a page had both a "detail" view and a "list/summary" view of the same data, the earlier remediation pass (documented in `RISK_REGISTER.md`) fixed the detail view but not always every sibling widget on the same page — an "upcoming/alert" banner, a leaderboard, an edit-modal attribute, or a page-header title built from the same tainted field.

**This was NOT fixed in this phase.** Per this repository's own process discipline (`ENGINEERING_PROCESS.md`) and the explicit instruction not to bundle unrelated work into this commit, these 41+5 findings are documented and prioritized as the next item, not silently absorbed into this pass's scope.
