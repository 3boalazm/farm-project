## assistant.html — treated separately, as instructed

The LLM's own output is untrusted input, not a special case exempted from escaping. Four sinks fixed:

1. **`addMsg()`** — the single choke point for every chat bubble (user input, LLM `info`/`clarify` responses, error messages). Previously did `div.innerHTML = String(text).replace(/\n/g,'<br>')` with no escaping. Now: `escapeHtml(String(text)).replace(/\n/g,'<br>')` — escape first, then convert literal newlines to real `<br>` tags. Order matters: escaping after the `<br>` conversion would have broken the intentional line breaks. One caller (`parsed.action==='info'`) was pre-converting `\n`→`<br>` itself before calling `addMsg`; that redundant call was removed so it doesn't double-process.
2. **`showConfirmation()`** — the pre-save "extracted data" preview. `parsed.summary` and any `data` key/value the LLM invented (not found in the fixed `fieldLabels`/`valueLabels` lookup tables) are now escaped.
3. **`editAndConfirm()`** — the edit modal's `mother_tag`/`notes` `value="..."` attributes, populated from LLM-extracted data.
4. **`showFarmContext()`** — escaped only at this HTML-rendering sink, deliberately **not** at `_farmContext`'s source, since that string is also concatenated as plain text into the LLM system prompt — escaping it there would corrupt what the model actually receives.

**Explicitly not claimed:** escaping these sinks fixes the *rendering* half of the risk (arbitrary HTML/script the model outputs can no longer execute). It does **not** address prompt injection — a tainted farm-data field (e.g., a medicine name) riding into the model's context, or a directly jailbroken response, could still cause the model to extract wrong data, recommend a wrong action, or produce a misleading `summary`/`answer`. That is a separate, unresolved business-logic/trust concern, tracked here as **REQUIRES FUTURE HARDENING**, not closed by this fix.

## pages/pedigree.js — treated separately, as instructed

Accessibility, Arabic names, and normal breed/tag rendering all confirmed unaffected.

## Round 5 — a sixth independent re-scan, commissioned specifically to NOT trust Round 4's own "0 findings" claim

Round 4 closed with a 0-finding pass and declared the acceptance gate met. That claim was itself re-tested: a fresh agent, given zero prior context and instructed explicitly not to trust any earlier round's report, re-scanned the entire repository (every root `.html` file, every `pages/*.js` file, plus every other root `.js` file) against the same vulnerability class, and additionally spot-checked 12 of the 152 then-existing Check 4 entries by reading current source directly (all 12 confirmed genuinely fixed — no stale entries found).

**Result: the "0 findings" claim was wrong.** Two more genuine, in-scope sinks were found:

1. **`assistant.html`'s `showConfirmation()`** — the LLM-JSON `fieldLabels`/`valueLabels` fallback branches were correctly escaped (see the `assistant.html` section above), but the adjacent `actionLabels[parsed.action]||'عملية'` fallback, one line above, was missed. `parsed.action` is LLM-controlled JSON, reachable both directly (a user can ask the model to emit an arbitrary `"action"` value; the API only enforces JSON syntax, not an enum) and indirectly (farm data concatenated into the system prompt on every message is itself attacker-writable, a prompt-injection path).
2. **`animal-detail.html`'s `renderWeightAlertsSection()`** — `a._id` and the URL-derived `animalId` are re-embedded into an `onclick="window.resolveWeightAlert('...')..."` JS-string argument without `escapeJsAttr()` — the same bug class Round 4 pass 3 fixed in `pages/inventory.js`'s `openUseModal()` (a value that is both an HTML attribute and a JS-string literal needs escaping for both contexts, and escaping it at a caller does not protect a different function that re-embeds it again). Classified defense-in-depth rather than currently-exploitable: the vulnerable branch only fires for a `weight_alerts` record whose `animal_id` field exactly matches the URL parameter, and that field is only ever set from a real Firebase-generated animal id, never free text — but fixed anyway, since leaving a known-unescaped re-embedding path in place is exactly the shape of bug this initiative kept re-discovering.

Both fixed with the existing helpers, syntax-checked, added to Check 4, verified against the full regression suite (39/39), and the guard itself was re-verified with a controlled regression test (temporarily reverted one fix via a backed-up copy — not `git checkout`, per this session's recovery discipline — confirmed the scan reported CRITICAL, restored, confirmed a clean re-scan).

**A separate, real, explicitly OUT-OF-SCOPE finding surfaced during this scan, not fixed here:** `farm-apk/www/` — the Capacitor Android-app copy of this codebase, synced by `scripts/sync-apk-www.js` — is not in sync with root and predates Round 1 entirely (`grep -c "escapeHtml("` returns 0 across every sampled file in that directory; `farm-apk/www/firebase.js` doesn't even define the helper). This means the previously-built `farm-apk.zip` and any Android build from this copy ships with **none** of the 154 fixes in this document. This is a real, security-relevant finding, not a false positive — but resyncing `farm-apk/www/` is a distinct, larger action (running `scripts/sync-apk-www.js` against ~90 files, a separate deliberate step) outside this initiative's declared scope of hardening the root web app, and is not performed here. Tracked in `docs/repository/RISK_REGISTER.md` as a new, separate risk entry.

It makes **no claim** about production behavior: no production deployment, Firebase rules publish, or Vercel deploy has occurred as part of this initiative, and none of this XSS work has been pushed to any remote.
