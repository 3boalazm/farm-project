# SYSTEM-MODEL.md

## Frontend Architecture
Vanilla, buildless multi-page app. 31 HTML pages, no client-side router, no bundler. Common script chain: `config.js → firebase.js → nav.js → shared.js → offline-sync.js → pages/<feature>.js` (delegated pages) or fully inline (16 pages). Entry point `index.html` redirects based on `localStorage['farm_user']` presence.

## Data Architecture
Firebase RTDB over REST, no SDK. `firebase.js` is the sole data layer (`fbGet/fbPost/fbPatch/fbPut/fbDelete`), ~45s in-memory cache, invalidated on write. Weight (`animals/{id}/weights`) and Birth (`breeding`+`animals` via `createOffspringAnimal()`) are certified SSOT. `genId()` (timestamp+random) produces human-readable reference codes, not primary keys — Firebase's own auto-generated `_id` is the real document identifier everywhere.

## Security Architecture
Custom PIN auth (not Firebase Auth), `hashPin()` (SHA-256, salted), `signInWithFirebaseAuth()` as a fail-safe secondary bridge for `auth.uid`/rate-limiting. `database.rules.json` enforces data validation only, not access control — access control lives entirely client-side via `can(perm)`, checked against `ROLE_PERMS`. **This session's audit found and fixed 10 pages missing this check entirely** (see `PERMISSION-MATRIX.md`).

## Offline Architecture
Two independent mechanisms: `sw.js` (byte-level HTTP caching, complete but not registered anywhere) and `offline-sync.js`/`FarmOfflineSync` (IndexedDB write queue, genuinely independent of the service worker). `sw-register.js` exists, is correct, but is not loaded by any page — the entire SW/PWA layer is built and dormant, a deliberate, documented state.

## Deployment Architecture
Vercel static hosting + two serverless functions (`api/claude.js`, unused by the client; `chat.js` was a misplaced duplicate, removed at commit `4b1e8cf`). Android APK is a separate Capacitor project (`farm-apk/`), pulling from the same Vercel-deployed web app.

## 2026-10 addendum — what the hardening pass changed in this model

* **Trust boundary moved server-side.** `database.rules.json` now decides who may
  read/write what (43/48 collections generated by `scripts/apply-access-policy.js`,
  resolving `uid_lookup/{auth.uid}` → `users/{id}` → `role`/`active`). Client-side
  `can()`/`canWrite()` is UX and defence in depth only; `custom_perms` grants are
  UI-only because RTDB rules cannot test array membership.
* **Session is verified, not assumed.** `verifySession()` on every boot; an outage
  yields `reason:'unverifiable'` and keeps the session (a farm must not be logged
  out by a network blip), while `role-mismatch`/`deactivated` clear it.
* **Writes are idempotent-aware.** `_writeFetch()` retries PUT/PATCH/DELETE on
  network failure and 429/5xx, never retries a POST that got no response, and does
  nothing while offline. Submit handlers mint `operationId` from
  `idempotencyKey(scope)` (sessionStorage-backed) so a double click cannot create
  two records — the engine's dedupe was previously unreachable because every click
  generated a fresh id (audit O-04).
* **Losses are expenses.** `computeFinanceKPIs()` counts a loss in
  `expenses`/`netProfit`/`roi`/margin/`avgCostPerAnimal` and reports it separately
  as `losses`/`lossCount`, with `operatingExpenses` for the rest (audit O-06).
  Historical records are untouched, and the legacy-migration analyser still treats
  `loss` as ambiguous by design.
* **Weather alerts follow one ladder** (`notifications-service.js`, audit O-16):
  ≥40 severe heat, ≥35 heat, ≤5 severe cold, ≤12 cold, humidity >85 respiratory,
  swing ≥8 change, otherwise a daily all-clear; each keyed once per day. The
  all-clear keys off *conditions matched*, not notifications emitted — keying off
  `fired` announced fine weather on the second poll of a heatwave.
* **Errors are observable.** A 40-entry diagnostics ring plus `app_logs` upload
  (`diagnostics()` / `flushDiagnostics()`), surfaced in `settings.html` (audit O-17).
* **The browser suite is hermetic.** `tests/fixtures/farm-test.js` serves every
  `*.firebasedatabase.app` / `*googleapis.com` request from the same in-memory fake
  the unit layer uses, so no spec touches the production project (audit O-19).
